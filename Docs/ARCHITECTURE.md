# Prototype architecture

The Combat Lab uses intentionally narrow seams:

1. PlayerInputSource samples devices and emits PlayerIntent.
2. ThirdPersonMotor consumes intent and owns player locomotion, facing the actual horizontal travel vector while moving, stop-and-turn handling for sharp reversals, a takeoff-captured airborne speed ceiling, responsive speed-capped air steering, center-supported edge grounding, jump forgiveness, variable jump height, crouch collision, and overhead-clearance validation while exposing read-only state for presentation.
3. HumanoidAnimatorPresenter reads motor state and feeds an Animator without mutating gameplay movement. The Humanoid runs in-place with root motion disabled. A conventional planted walk is paired with a CC0 KayKit run retargeted into generated tactical jog/sprint clips. Walk travel and clip playback are raised proportionally to 1.85 m/s and 0.695x so the accepted foot path remains synchronized. Run generation removes source yaw, keeps the spine and gaze upright, tucks the upper arms while preserving their front/back swing, maintains positive foot separation, and phase-aligns the loop to enter on a planted contact without changing the accepted leg curves. Playback rates remain matched to the 4.6 m/s sprint target. Speed-blended standing and moving rise poses switch to fall from motor vertical velocity and leave the airborne state immediately on ground contact. The stationary tactical rest places the rear knee and heel at the floor, plants the forward sole, straightens the spine, and relaxes the arms. The playable controller adds a finger-only right-hand sword-grip layer and an upper-body-only three-hit attack layer above locomotion. The short sword remains parented to the closed hand in its established carry position. ProceduralHumanoidPresenter remains only as an import-failure fallback.
4. CameraAimTarget converts look intent into a smoothed world-space aim transform, lowers with crouch, and clamps below detected ceilings; Cinemachine owns follow, shoulder framing, and collision presentation.
5. ShortSwordAttackPresenter owns the restored regular three-hit presentation, its per-hit input windows, recovery states, first-sweep IK correction, swing audio, and return blending. UpperBodyAimPresenter turns the torso toward camera/cursor aim. MeleeWeapon owns a single active strike at a time and samples a swept capsule along the visible blade; damage and impact feedback begin on first contact rather than from a detached proximity volume. Anatomical colliders are canonicalized to their owning health/profile for per-swing deduplication, so crossing several bones on one humanoid still produces one 60-damage sword event and one floating number.
6. DamageService resolves an IDamageable owner; Health is the only component that mutates health.
7. EnemyBrain retains replaceable enemy state logic but currently runs in passive training-dummy mode; EnemyTelegraphPresenter only visualizes state.
8. GameplayEventLog records meaningful combat state changes without making game systems depend on presentation.
9. LocomotionDebugOverlay provides an opt-in F8 live readout of motor speed, velocity-facing error, pose-facing error, head motion, foot spacing, foot height, hand spread, active clip weights, and full-scene recording status.
10. GameplayDiagnosticRecorder is a normally passive observer. F9 records natural free play and F10 adds an event-aligned screenshot marker. Schema-v2 captures correlate input, motor, physics, current/next Animator state, calibrated Humanoid pose and sole probes, crouch geometry, camera, weapon, damage, health, enemy state, and gameplay events into a versioned timestamped artifact bundle. Deterministic sample time is kept separate from wall time so screenshot or Editor stalls cannot distort simulation metrics. Each report also snapshots its source revision and effective motor, Animator, weapon, and camera configuration; an interrupted free-play capture is persisted as aborted rather than discarded.
11. CombatLabDiagnosticScenarioRunner uses the diagnostic override at PlayerInputSource—the existing input ownership seam—to drive a frame-locked full-scene movement and combat suite through production code. It is an Update-driven transaction: the named phase and intent are committed before production input and simulation, then the recorder observes the result in `LateUpdate`. Independent right and left sprint turns prevent a directional bias from hiding inside a combined test. A run can pass only after every required phase completes exactly once and a completion event is observed; early Play-mode exit, timeout, Unity error, or explicit cancellation records an abort instead of accepting a partial run.
12. The Editor diagnostics orchestrator manages Play mode, source capture, errors, batch exit status, creator reviews, and baseline comparisons. Baseline promotion requires a completed, functionally passing current-schema deterministic run plus a persisted **Accepted** review that names that exact run. No schema-v2 baseline is currently accepted.
13. LocomotionDiagnosticsRunner immutably evaluates the existing Humanoid Animator controller at 60 samples per gait and writes machine-readable telemetry plus 16-pose front/side/rear contact sheets. It never regenerates the assets it measures.
14. PlayableRigValidation protects the future weapon-animation authoring boundary. Blender will author against the exact playable hierarchy and emit a contracted intermediate FBX. Unity can validate transport, timing, pose sampling, and isolated controller playback before any clip is wired into Combat Lab. Existing pose-blockout and attack assets are research only.
15. CombatLabSceneBuilder creates the disposable greybox scene reproducibly and attaches the passive recorder.

This is multiplayer-aware rather than multiplayer-built. Input, requests, authoritative owners, stable IDs, and event records create future evaluation seams. No current code promises that multiplayer conversion will be automatic.

## Next proof sequence

1. Playtest and tune the restored three-hit combo, especially its continuation windows, first-sweep reach, contact timing, and return-to-ready transitions.
2. Replace the prototype combo only after a candidate animation has been approved in isolation and validated on the exact playable rig.
3. Add one valuable pickup, a clear extraction zone, death, and a small consequence.
4. Test a reduced Weapon Grid with only a few artifacts and one meaningful tradeoff.
5. Assemble a raid from authored chunks with stable connectors and a deterministic seed.
6. Add pseudo-player NPC behavior only after combat spaces and extraction pressure exist.
